模型这一侧看到的全部输入

system 消息 —— 协议约定（react.py · SYSTEM_PROMPT）
三条硬约束：每轮只许一组 Action / 绝不自己写 Observation / 事实够了就输出 Final Answer。
user 消息 —— 拼出来的那一根字符串（build_prompt()）
两行工具目录（ToolSpec.catalog_line()）＋ 输出格式约定（TASK_TEMPLATE）＋ 问题。 第一次 378 字符；此后每次工具返回都追加一行 Observation:，并以 Thought: 结尾提示模型继续。
采样参数
temperature 0.0（可复现）、stream false；max_tokens 不发送，保持服务端默认。
native 模式的差别
同样两个工具，但以 tools[]（JSON schema）随每次请求发送，并带 tool_choice: "auto"。
密钥
只从环境变量 DEEPSEEK_API_KEY 读；Authorization: Bearer … 由客户端加上，落进 wire.jsonl 的只有请求体。

第一次 POST 的请求体（结构）

{
  "model": "deepseek-chat",
  "messages": [
    {"role": "system",
     "content": "你是一个 ReAct 智能体。三条硬约束：…"},
    {"role": "user",
     "content": "可用工具（每轮只能用一个）：\n
                 - calculator[expression]: …\n
                 - search_docs[query]: …\n
                 Thought / Action / Action Input 格式约定…\n
                 问题：…"}
  ],
  "temperature": 0.0,
  "stream": false
}
两轮之间变化的只有 user 消息的那根字符串——system 与参数一个字节都没动。

模型最后给出的答案（已截断）

做「目录级 AUTH_OPEN」的项目是 es-mvp（用 Endpoint Security 的 AUTH_OPEN 事件做目录级拦截，采用反向静音策略）。它的规范文档是仓库内的 es-mvp/SPEC.md，实测结论写在该文件的 §9，共三条：一、反向静音在真实硬件（macOS 26.5.2）上验证通过……

原文 316 字符，存于 result.json 的 answer 字段；stopped_reason 为 final_answer，tool_calls 为 1。

轨迹里没有一个"计划"对象：下一步完全由上一轮的工具输出决定。

工具：一套 handler，两种协议

文本协议看到的两行目录（进 prompt）
- calculator[expression]: 计算一个纯算术表达式（支持 + - * / // % ** 与括号）
- search_docs[query]: 在本地文档库中检索（返回命中的文档 id、标题与正文片段）
native 模式的等价物（进 tools=）
同一个 ToolSpec 生成 JSON schema：{"type":"function","function":{"name":"calculator","parameters":{"properties":{"expression":{"type":"string"}},"required":["expression"]}}}
失败不炸循环
未知工具、缺 Action Input、handler 抛异常 —— 三种情况都变成一条可读的 Observation（ok=false），模型据此自我纠正；观察输出封顶 2000 字符。
模型自己写 Observation 时
解析阶段直接在第一个 Observation: 处截断，防止幻觉回填进上下文——这是与"提示词里叮嘱十遍"不同的确定性防线。
